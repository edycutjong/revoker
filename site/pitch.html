Revoker

TypeScript · Solidity 0.8.28 + Foundry · viem · KeeperHub · Ethereum Sepolia

Revoker is an autonomous on-chain security agent. One sentence: when a token approval turns dangerous, it revokes it through KeeperHub before a human could even read the alert. Everything in this deck happened on Ethereum Sepolia, and every number is a transaction you can open.

The most common wallet-drain vector

approve(spender, MAX_UINT256)

You signed it once, months ago. It never expires — and the day that contract turns malicious, the allowance is still live.

Ask the room: who here has clicked "approve unlimited" to save gas? That signature never expires. Months later the spender contract turns malicious — and the allowance you forgot is still armed. This single line of calldata is the most common way wallets get drained.

The problem

Every tool stops at the alert.

Approval checkers are read-only: they rate the risk, list the allowance — and leave the acting to you. For a wallet holder with forgotten approvals, or a keeper wallet with no human attached, an alert is not protection.

APPROVAL RISK — HIGH

A spender you approved has been flagged. Your allowance is unlimited.

Acknowledge

The state of the art ends here — a notification, and a button that does nothing on-chain.

The entire industry answer today is a dashboard and a push notification. Detection without execution is not protection: by the time a human wakes up, reads the alert, opens a wallet and signs, the drain has cleared. That gap between knowing and acting is the product.

The solution

Revoker acts.

An autonomous agent that watches a wallet’s live approval set and executes approve(spender, 0) through KeeperHub the instant a threat rule fires — no human in the loop.

How it works

One loop. No human.

Second ledger

That loop runs over two allowance ledgers, not one. Permit2 — the shared approval contract most of the ERC-20 ecosystem routes through — keeps its own. A grant written there changes nothing in the token and emits no Approval event, so every watcher built on those logs is blind to it by construction. Revoker reads both, and revokes Permit2 with lockdown(): however many slots, one transaction.

The whole system is one loop: read the chain, evaluate four auditable rules plus a hold channel — no ML, every firing carries its evidence — and hand execution to KeeperHub. Note what the agent never touches: a private key. Signing happens inside a Turnkey enclave, and every execution lands in an audit trail you can watch live on the local dashboard. And that loop runs twice over — because Permit2 keeps a second allowance ledger the token contract never sees. A grant written there emits no Approval event at all, so every watcher built on those logs is structurally blind to it. We watch both, and we clear Permit2 with lockdown, which zeroes every fired slot in a single transaction.

Scope · stated plainly

Known limits, on the record.

A security tool that hides its blind spots is part of the problem. These are Revoker’s.

Sepolia testnet only

The mainnet path is documented, not executed. No real funds were risked producing any number in this deck.

Token discovery is watchlist-scoped

No public RPC serves an address-less eth_getLogs over a useful range. Revoker protects the tokens it is told to watch — not coverage it doesn’t have.

young-spender abstains loudly

Without an archive RPC it returns INDETERMINATE and names the remedy — instead of silently reporting “safe”.

The threat model is narrow on purpose

A spender that is verified, aged, and off the deny-list trips nothing. That case is out of scope, not silently mishandled.

We would rather tell you the limits than have you find them. Testnet only. Discovery is watchlist-scoped because no public RPC can enumerate approvals honestly. The young-spender rule abstains loudly when it can't see instead of rubber-stamping. And the threat model is deliberately narrow — an agent that moves funds should only act on rules it can defend.
